1. 실제 확인한 문제

P0. 평가 모집단 혼합
- cap_run.py는 milestone(5/10/15/20)에서 post['summary']=ALL_SEEN,
  나머지는 post['summary']=CURRENT를 사용한다.
- cap_tracking.log_endpoint가 이를 모두 eval/RS, eval/PS, eval/NS에 기록한다.
- 원격 60001의 R denominator는 edits 100/200/300/400에서100,
  edits500에서500, edits600에서100이다. 하나의 동일 모집단 곡선이 아니다.
- 올바른 current/post는 항상 post['current']; all_seen/post는 milestone의
  post['summary']만 기록한다. 미측정 milestone 외 all-seen은 key를 생략한다.

P0. R/P/N 지표의 같은 키 사용
- eval/TF_token_micro, eval/TF_prompt_macro, eval/TF_strict,
  eval/true_nll, eval/new_nll에 R/P/N을 순서대로 기록하고 phase_id=3/4/5만 사용.
- 기본 차트는 세 모집단을 한 선으로 연결하며 summary는 마지막 N 값이다.
- R/P/N을 경로에 명시해야 한다. N desired target=true, R/P=new 유지.

P1. 과거와 metric key 및 단위 불일치
- 과거 PRICE-59768: current/post/R/success_pct, all_seen/post/R/success_pct 등,
  0..100 백분율. 현재 60001: eval/RS 등 0..1 rate.
- 단순 이름 alias 또는 곱하기100만으로 P0 모집단 혼합은 해결되지 않는다.
- RS=R success, PS=P success, NS=N success. Strict/token/prompt ACC와 별개다.

P1. x축 불일치
- 과거 _step은 대체로 batch 단위, 새 _step은 candidate와 eval 호출 단위.
- 모든 성능 곡선은 edits를 x축으로 지정하고 같은 log payload에 edits 포함.
- 과거 호환 current/pre의 edits는 해당 birth batch의 post 위치이다.
  실제 pre 평가 상태는 (batch-1)*100이므로 pre-state와 post-state를 혼동하지 말 것.
- fit candidate는 batch마다 재시작하므로 fit용 축을 평가 edits와 구분할 것.

P1. 비교에 필요한 관측이 raw에 있으나 online caller가 누락
- 현재 caller는 post만 전송; W0 및 current/pre는 해당 online run에서 미전송.
- milestone current100은 raw의 post['current']에 있지만 같은 caller가 누락.
- raw가 존재하면 CPU 재집계만으로 보완. 새 GPU forward/evaluation/fit 불필요.

P1. 모델/writer 명시 필드 부족
- 공통 helper CONFIG_KEYS에는 model/writer/role이 없다.
- 현재 run은 arm=LLAMA_CAP075, job_id=60001이지만 model 필드 없음.
- 모델별 view 포함 여부와 metric 비교 호환성은 서로 다른 문제다.
- SH1 소유 helper의 allowlist 확장 협의: model(llama3/gptj/qwen),
  writer(memit/alphaedit), role(scientific/derived_comparison_snapshot),
  metric_schema, source run link. raw config나 전체 env를 허용하지 말 것.

P1. 온라인 상태/완료 의미
- receipt.json의 LOGGING_ACCEPTED는 SDK_ASYNC_NOT_REMOTE_ACK이며 전송 완료 증명이 아님.
- 최신 이벤트로 result가 교체되어 초기 url이 사라질 수 있다. 별도 불변 run identity
  receipt(run_id/url/job/source/config)와 가변 transport receipt를 분리해야 한다.
- 비교 snapshot run의 finished는 uploader 종료이지 실험 완료가 아니다.

3. 후속 구현 계약 (기존 봉인 job hotpatch/재시작 금지)

새로 봉인하는 source에서는 생산 caller와 SH1 공통 helper schema를 함께 맞출 것.
현재 pending job도 이미 archive/lock이 봉인됐다면 파일만 바꿔서는 반영되지 않으며
무단 취소/재제출하지 않는다. owner에게 변경된 source 적용 경계를 확인할 것.

표준 prefix:
  current/pre/{R,P,N}/*
  current/post/{R,P,N}/*
  all_seen/post/{R,P,N}/*  (실측 milestone만)
  W0_first2000/{R,P,N}/*  (cold first2000만, 과거10k와 합치지 않음)
  w0/current/N/*, w0/all_seen/N/* (정확 동일 cohort의 W0 비교)

각 prefix/kind의 scalar:
  count, success_count, success_pct, token_acc_pct, prompt_acc_pct,
  strict_acc_pct, true_nll, new_nll, margin_true_minus_new
  필요하면 desired_nll(R/P=new, N=true), token numerator/denominator와
  strict count를 명시적으로 확장. 존재하지 않는 값을 만들지 않는다.

각 R/P/N 세트의 prefix/success_harmonic_pct:
  성공 rate가 모두 양수일 때 300 / (1/RS + 1/PS + 1/NS),
  하나라도0이면0. strict ACC의 조화평균이 아니다.

모든 rate는 *_pct 키에서100배. NLL은 원 자연로그 단위 그대로.
margin_true_minus_new=true_nll-new_nll, 반대 부호는 다른 이름으로 저장.
count와 success_count는 정수; 결측은 생략 또는 별도 availability, 0 대입 금지.

단일 batch commit 후 caller 예시:
  log({edits:b*100, **map('current/pre', pre['summary']),
       **map('current/post', post['current']),
       **(map('all_seen/post', post['summary']) if b in [5,10,15,20] else {})})
  define_metric('current/post/*', step_metric='edits', step_sync=False)
  다른 eval prefix도 동일. 같은 endpoint를 새로 forward하지 않는다.

현재 helper METRICS는 고정 whitelist라 위 경로를 추가하지 않으면 거부된다.
caller만 새 key로 바꾸면 LOGGING_DEGRADED_CALLER/dropped point가 발생할 수 있다.
SH1 helper 단독 소유를 존중하며, caller와 schema를 원자적으로 검증/봉인할 것.
